# Анализ организационной структуры и функционала

Кейс выбран пользователем 2026-09-23; разрешено продолжить по скиллу. Рабочий объём первой версии ниже. Продукт ещё не реализован.

## Результат и обязательный объём

Сотрудник загружает комплекты Word/PDF/Excel до/после реорганизации. Получает:
1. Сохранённые, созданные и преобразованные подразделения, включая слияние/разделение.
2. Матрицу функций до → после, включая нормально сохранённые функции.
3. Возможные потери, дублирования и конфликты интересов.
4. Для каждого существенного вывода — точные фрагменты исходников.
5. Понятное аналитическое заключение с ограничениями и короткими рекомендациями уточнить ответственность.

Источник: docs/CASE_BRIEF.md; подробный анализ — ORG_CASE_REVIEW.md. Техническая шкала 25/25/25/15/10. Внешние нормы, бенчмаркинг операторов и проектирование новой структуры — за пределами первой версии.

## Обработка

Чтение документов с устойчивыми адресами → извлечение подразделений и функций → смысловое сопоставление → агентная проверка неоднозначностей → проверка доказательств → отчёт.

Для функции сохраняются действие, объект, область, исполнитель, полномочие/роль, версия и источник. Допускаются связи один-к-многим и несколько-к-одному. Название отдела само по себе не определяет сохранность функций.

Один агент использует search_functions, read_evidence, get_unit_relations, validate_finding. Если функция не найдена у прежнего исполнителя, ищет перенос и переформулировку, открывает контекст и проверяет кандидата. Логируются фактические вызовы инструментов и результаты, не внутренние рассуждения. Полный реестр извлечённых функций и покрытие документов обязательны: выборочный поиск их не заменяет.

Файлы и расчёт адресов обрабатывает код; семантические соответствия предлагает модель. Наличие цитаты и поддержка вывода её смыслом проверяются отдельно. Количество шагов, размер ввода, повторы и время ограничиваются конфигурацией при реализации.

## Доказательства и ограничения

- Word: пункт/абзац/таблица. PDF: страница/фрагмент. Excel: лист/ячейки. Не придумывать страницы Word, зависящие от вёрстки.
- Скан/изображение/непрочитанная таблица — видимая проблема покрытия. Проверить потребность OCR на реальном комплекте, не обещать поддержку любого файла.
- Возможная потеря: цитата до, проверенный комплект после и формулировка «назначение не найдено в предоставленных документах». Это не доказательство отсутствия во всей организации.
- Дублирование: одинаковые действие/объект/область. Подготовка и утверждение могут быть нормальным разделением ролей.
- Конфликт: обе роли и основание предполагаемой несовместимости. Если правило разделения отсутствует — гипотеза для сотрудника, не нормативное нарушение.
- Нечитаемый или отсутствующий материал означает «недостаточно данных».
- Статус проверки сотрудником отделён от вывода AI. Сначала показываем «не проверено»; сохранение подтверждений/отклонений — следующий этап.
- Никаких необоснованных процентов уверенности. При сбое модели не показывать заранее записанный отчёт как результат AI.

## Приёмка первой версии

| Случай | Проверка |
| --- | --- |
| Реорганизация | Правильные связи подразделений с источниками |
| Потеря | Цитата до, охват после, осторожный вывод |
| Дубль | Два источника и одинаковая обязанность |
| Потенциальный конфликт | Две роли, источник правила при наличии, причина риска |
| Переименование/перенос | Нет ложной потери |
| Подготовка и утверждение | Нет ложного дублирования |
| Пустой комплект/плохой файл | Понятная ошибка или неполнота, не ложный полный результат |
| Сбой модели | Ошибка и ограниченный повтор, сохранённые исходники |
| Открытие замечания | Правильная цитата и версия |
| Независимый запуск | Друг воспроизводит сценарий по README |

Первый рабочий этап: настоящая загрузка → извлечение → модель и её инструмент → замечание с открываемой цитатой в UI. Это промежуточный результат, не закрытие всех must-have.

## Архитектура и владельцы

Предложение: один Python backend, браузерный интерфейс, файловое хранение одного локального пользователя. Конкретный фреймворк, парсеры и модель выбираются при рабочей основе и проверке зависимостей. Отдельная графовая/векторная БД и много сервисов не нужны. API_CONTRACT.md r1 — проект договора, маршруты ещё не реализованы.

Капитан: backend, извлечение, AI, проверка доказательств, тесты. Друг: frontend загрузки, матрица, карточки замечаний, панель источников; затем независимый запуск. Задание — TEAMMATE_TASK.md.

Ключ модели хранится на сервере; документы — данные, не команды. Адрес источника разрешается только внутри своего анализа, не как произвольный путь. Текст безопасно отображается без исполнения HTML. Модельные вызовы пока не выполнялись.

## Технический эксперимент и текущее состояние

Python 3.11.8 доступен. В основном Python нет docx/pypdf/openpyxl/fastapi/uvicorn/pytest. Это не утверждение об отсутствии в других окружениях. MarkItDown установлен отдельно, ранее прочитал DOCX ТЗ.

Реальные документы организатора до/после ещё не получены; пользователь пока не знает, где они. Подготовлен явно авторский комплект fixtures/org-review с эталонной разметкой. Он не проверяет Word/PDF/Excel и не заменяет реальный пакет. Главная проба на нём позже: функция → соответствие → точный адрес источника.

Проект должен находиться в собственном Git-репозитории, изолированном от родительских каталогов. Дедлайн, API-бюджет и модель пока не заданы.

Отложены: законодательство, сравнение операторов, кадровые рекомендации, автоматическое редактирование документов, сложная оргсхема и корпоративные интеграции.
