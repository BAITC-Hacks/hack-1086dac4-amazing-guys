# Проверка общей версии — 2026-09-23

Интерфейс «Контур» из коммита `25e4184` подключён к FastAPI; дополнительно объединён коммит товарища `dd9cbbf` с навигацией до анализа. Визуальный стиль сохранён; интеграционное изменение frontend касается только предела ожидания (10 минут).

## Исправления

- Большие документы: лимит считается по исходному тексту (250 000 символов), а не по многократно скопированному контексту. Каждый ID стоит непосредственно рядом со своей цитатой и версией; порядок сохранён, ни один фрагмент не отбрасывается. Полный соседний контекст доступен через read_evidence и API источников. Отдельный словарь повторяющихся текстов убран: на живой проверке модель путала его индексы с порядком source ID.
- Локальные порты 5173/4173/3000 разрешены для localhost и 127.0.0.1. CORS_ORIGINS добавляет дополнительные адреса; ключ остаётся только на backend.
- OpenAPI описывает фактический error-конверт вместо стандартного detail, а также health и HTTP-коды ошибок.
- Отчёт с некорректными ссылками получает не более одной модельной коррекции и повторную проверку; если она неуспешна, отчёт не публикуется. Максимум 5 запросов модели и оценочный бюджет $0.25 на анализ.
- Первое действие модели — поиск по комплекту после для проверки назначения функции с неочевидным правопреемником. Последующие инструменты выбирает модель.
- Колонтитул только с полем номера страницы не помечает весь документ как частично непрочитанный. Содержательный пропущенный текст по-прежнему вызывает предупреждение.
- Источники функций наследуются сопоставлениями и замечаниями по явно указанным связям, затем рекомендациями. Новые источники код не угадывает; исходные ошибочные или повторные ID не удаляет — их отклоняет проверка. Сборка отмечается в activity. Это передача происхождения данных, не подтверждение смысловой связи.
- Для строк подразделений добавлена узкая проверка: если точное название встречается в данной версии, нужен источник, в котором оно названо. Сообщение коррекции перечисляет проблемные строки и ID таких фрагментов. Проверка не распознаёт все склонения/сокращения и не доказывает корректность остальных цитат.
- Модельная схема ограничивает evidence_ids реальными адресами комплекта. Учитываются [лимиты Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): 1000 enum-значений в схеме и 15 000 символов для большого строкового enum. Обе предоставленные редакции помещаются (981 источник). При превышении ограничений используется обычная схема и тот же серверный валидатор, источники не отбрасываются. Публичный HTTP r1 не меняется.
- Внутреннее поле source_excerpt у функции должно дословно совпасть с фрагментом её цитируемого источника; соседний действительный ID с другим текстом не проходит. Это поле используется при проверке, в HTTP r1 не добавляется. Смысл функции и выводов по-прежнему требует содержательной проверки.
- Расход полученного ответа учитывается до разбора JSON, поэтому ошибка формата больше не теряет известный usage. После сетевого таймаута полного расхода по-прежнему может не быть.

По указанию пользователя добавлена настройка OPENAI_REASONING_EFFORT (по умолчанию medium; прежний none доступен для сравнения). Парсер, исходные документы, инструкции анализа и HTTP r1 сохранены. Промежуточному ответу выделено до 8192 выходных токенов вместо 2048, чтобы reasoning и вызов инструмента помещались в один ответ. Общие пределы 5 запросов, 600 секунд и оценочный бюджет $0.25 сохранены. Backend: 80 тестов прошли, включая передачу режима, ранний отказ неверной настройки и сохранение reasoning-контекста между вызовами инструментов.

Запуск medium `58b685899aae46c5b8f5459d01b0cbcc` завершён через тот же production preview: 200.947 с, 5 запросов, 363 521 входной / 21 295 выходных токенов, оценка $0.0469996. Fingerprint исходных файлов и все 981 извлечённый источник побайтно/структурно совпадают с baseline e651. Получены 42 функции, 21 сопоставление preserved, 1 insufficient_evidence. Все 42 ссылки функций соответствуют источникам, однако функции относятся только к §2.4. Это не более компактное представление прежнего полного набора: обязанности остальных разделов не включены, что модель прямо признаёт в limitations.

Прежние неточности f3/m65 в medium не повторены, но соответствующие обязанности вообще исключены из анализа; это не доказательство исправленного понимания. Более узкий результат и явное ограничение охвата подтверждены независимым чтением отчёта. Улучшение качества medium на этой паре не подтверждено; одиночный прогон не устанавливает универсальное превосходство одного режима. Следующая гипотеза — контролируемый обход разделов/сопоставление изменённых пунктов при сохранении Luna; такой механизм сейчас не добавлен. Эталонные ответы модели не передавались.

В пропущенных ранее §9.15 и §9.37 текст успешно извлечён парсером и передан модели: проблема выявлена на этапе выделения функций и сопоставления смысла, а не в чтении этих абзацев DOCX. Более сложный парсер может понадобиться для сканов/сложной вёрстки, но не считается исправлением обнаруженных смысловых пропусков без отдельной проверки.

Варианты для будущей проверки чтения: [python-docx](https://github.com/python-openxml/python-docx) уже используется для DOCX; [Docling](https://github.com/docling-project/docling) поддерживает структуру PDF, таблицы и OCR; [MarkItDown](https://github.com/microsoft/markitdown) преобразует документы в Markdown. Новые парсеры в этой проверке не устанавливались.

После живого сравнения подтянут коммит товарища 225a4ef с переходами и загрузкой источников. Production build успешен; 22 браузерные проверки Chrome прошли за 31.8 с. Это регрессия UI с контролируемыми ответами, не дополнительный платный модельный прогон.
