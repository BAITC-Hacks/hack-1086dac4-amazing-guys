# Авторский контрольный комплект: организационная структура

**Это синтетические документы команды, не данные организаторов.** Компания «Контур», её подразделения и изменения вымышлены. Комплект подготовлен для обсуждения требований и будущей проверки; он не подтверждает качество работающего продукта.

- `before.md` — состояние до реорганизации, версия BEFORE-1.
- `after.md` — состояние после реорганизации, версия AFTER-1.
- `expected.json` — эталон пяти контрольных случаев и ожидаемого сопоставления подразделений.

Каждый значимый пункт имеет устойчивый ID в квадратных скобках. Ссылка на источник состоит из имени файла и ID; цитата хранится отдельно и должна точно совпадать со всем текстом соответствующего пункта после ID.

## Контрольные случаи

| ID | Случай | Ожидаемый результат |
| --- | --- | --- |
| C1 | Подтверждённое переименование и перефразированная функция | Сохранённая функция, не потеря и не новое независимое подразделение |
| C2 | Старая функция не найдена в новом комплекте | Потенциальная потеря с указанием проверенного охвата; отсутствие в реальной компании не доказано |
| C3 | Два отдела ведут один реестр на одинаковых условиях | Возможное дублирование с двумя источниками |
| C4 | Один отдел выполняет и независимо контролирует свои платежи | Потенциальный конфликт с двумя назначениями и явным правилом разделения |
| C5 | Один отдел готовит план, другой утверждает | Разные этапы, не дублирование и не конфликт |

`status` — ожидаемая категория вывода, а не статус реализации теста. `sources` — подтверждающие или контекстные пункты. Для C2 `search_scope` перечисляет весь просмотренный документ «после»; `matched_successor_function_ids: []` означает отсутствие найденного назначения только в нём. Одного приказа об упразднении недостаточно для вывода о потере функции.

`expected_unit_mapping` дополнительно проверяет переименование, сохранение, упразднение и создание подразделений. В C4 контрольная функция сохранилась, но перешла исполнителю платежей; её нельзя одновременно объявлять утраченной.

## Будущая приёмка прототипа

Передавать анализатору только `before.md` и `after.md`. **Не включать `expected.json` в контекст модели, извлечение или поисковый индекс.** Сравнивать результат с эталоном после анализа. Произвольные формулировки допустимы, если сохраняются смысл, категория и правильные источники.

Отдельно учитывать обнаруженные и пропущенные контрольные случаи, ложные тревоги и точность цитат. C1 и C5 — обязательные отрицательные примеры для тревог; C2 требует явного ограничения вывода предоставленным комплектом. C3 и C4 остаются рекомендательными находками для проверки сотрудником.

## Границы этой фикстуры

Markdown проверяет смысл сопоставления и адресацию свидетельств. Он не проверяет извлечение Word/PDF/Excel, OCR, таблицы, колонтитулы, объёмные комплекты, доступность модели или устойчивость к инструкциям внутри документов. Здесь нет реальных персональных данных, внешних нормативов, измерений качества или доказательства отраслевой применимости. Все пять случаев заранее заданы и не заменяют независимую проверку на данных организаторов.
